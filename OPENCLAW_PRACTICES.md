# Pratiques OpenClaw retenues pour FXMP OS

Le moniteur de ressources utilise la commande native en lecture seule `get_resource_sample`, limitée à la capacité `main`. Elle collecte CPU, mémoire et métadonnées limitées des processus localement, avec une liste bornée à l'union des 25 premiers en CPU et des 25 premiers en mémoire. Les champs de processus restent limités au nom, PID, CPU normalisé sur 0–100 % machine et mémoire; aucun chemin, argument de lancement, utilisateur ou action de contrôle n'est permis.

Revue ciblée d'OpenClaw effectuée le 18 octobre 2026 sur les surfaces liées à l'app Linux Tauri, au Windows Hub, aux mises à jour et à la sécurité; ce n'est pas un audit ligne par ligne de tout le dépôt. L'état FXMP OS de ce document a été réaligné le 28 octobre 2026 sur la version 0.0.38. FXMP OS est une application locale de monitoring; il ne partage pas le rôle de passerelle, de messagerie ou d'exécution d'agents d'OpenClaw.

## Ce que nous reprenons

| Domaine            | Choix retenu dans FXMP OS                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Permissions Tauri  | Des capacités locales séparées par fenêtre : `main` configure l'overlay, lit les écrans, gère l'updater, le store et les notifications; `overlay` ne lit que ses mesures compactes, peut se déplacer et partage les préférences via Store. Le dock et l'Input Viewer ont chacun une capacité minimale. Le menu tray natif n'ajoute pas de fenêtre WebView ni de capacité. Les commandes de collecte n'acceptent aucun chemin ou script fourni par l'interface.                                                                                                                                                                     |
| Contenu WebView    | La navigation externe est validée en Rust et les schémas non approuvés sont refusés. Les journaux n'enregistrent que l'origine ou le schéma expurgé, jamais chemin, requête ou fragment. Le CSP n'autorise que les ressources locales, les images `data:`/`blob:`, l'IPC Tauri et une lecture sans authentification de l'API publique `api.github.com` pour l'historique des releases; aucune donnée locale n'est envoyée à GitHub. |
| Travail natif      | La collecte système et WMI s'exécutent dans le pool de tâches bloquantes afin que l'interrogation du matériel ne fige pas le thread de l'interface.                                                                                                                                                                                                                                                      |
| Cycle de vie       | L'instance unique, le démarrage masqué optionnel, le démarrage Windows facultatif et la fermeture vers la zone de notification sont explicites. `main` a `create: false` et est construite depuis sa configuration avec `WebviewWindowBuilder::from_config` dans `setup`; l'overlay garde aussi `create: false` et n'est créé qu'à la demande par une commande asynchrone. Sous Linux, la commande interroge le backend GDK réellement sélectionné sur le thread principal et refuse Wayland avant de créer la WebView, car le placement global choisi par l'overlay exige X11. Les préférences ne sont enregistrées qu'après la réussite de la commande native; si leur écriture échoue, l'interface restaure l'état natif précédent. Quitter reste une action de tray séparée. Sous Windows, le hook natif `SetWindowSubclass` laisse passer `WM_QUERYENDSESSION` / `WM_ENDSESSION` avec `ENDSESSION_CLOSEAPP` envoyés par Restart Manager pendant le remplacement ou la désinstallation NSIS; cette fermeture d'installation est distincte de la fermeture utilisateur, qui masque toujours l'application dans le tray. |
| Zone de notification | FXMP OS construit le menu contextuel avec `tauri::menu::MenuBuilder`, l'attache à `TrayIconBuilder::menu`, traite les actions avec `on_menu_event` et réserve le clic gauche à l'affichage/masquage de la fenêtre principale. Le code suit le modèle du menu Tauri natif d'OpenClaw Desktop; aucune WebView ni bordure dessinée par FXMP OS n'est utilisée comme menu du tray. |

Le menu Tauri natif et la fenêtre WinUI du Hub sont deux implémentations OpenClaw distinctes. FXMP OS utilise l'API de menu Tauri pour obtenir le menu contextuel Windows du système; le Hub WinUI n'est pas ajouté comme dépendance runtime. Le modèle de construction Tauri suit [OpenClaw `tray.rs` au commit `c49e07385f8d17601efbed7746381213d5326ba9`](https://github.com/openclaw/openclaw/blob/c49e07385f8d17601efbed7746381213d5326ba9/apps/linux/src-tauri/src/tray.rs).
| Updater            | Les paquets sont signés, la version du manifeste est liée à la signature, l'utilisateur déclenche l'installation, les releases restent en brouillon après build, et une étape séparée normalise les URLs vers des téléchargements navigateur GitHub avant de vérifier les plateformes, les signatures et les sommes de contrôle.                                                                 |
| Origine de release | Un tag doit correspondre à la version Tauri. L'exécution manuelle de publication est limitée à la branche par défaut.                                                                                                                                                                                                                                                                                    |
| Vie privée         | Les détails du PC et les dimensions/positions d'écran sont lus localement. FXMP OS n'expose pas de numéros de série, EDID ou identifiants matériels uniques et ne transmet pas ces informations au manifeste de mise à jour.                                                                                                                                                                                |

## Notifications natives et toasts

FXMP OS utilise deux canaux indépendants : Sonner affiche les toasts dans l'application, tandis que `tauri-plugin-notification` envoie les notifications natives Windows. Chaque canal suit son propre réglage et les deux peuvent notifier le même événement, y compris lorsque la fenêtre principale est au premier plan. Les notifications système fonctionnent dans l'application installée; en développement, Windows peut les attribuer à PowerShell. La capacité `main` reçoit seulement les permissions de lecture de l'état, de demande explicite et d'envoi; `overlay` n'a aucune permission de notification. Le premier lancement ne déclenche jamais de boîte de permission. Les préférences partagées (activation, position, durée et bouton de fermeture) sont stockées dans `fxmp-settings.json`; le contenu des notifications ne doit jamais contenir de données système, processus, ports ou d'identifiants locaux. La demande d'autorisation est réservée au clic sur le bouton dans Paramètres.

La mesure de latence est une action explicite depuis la fenêtre `main`, vers la cible TCP fixe `1.1.1.1:443` avec des tentatives bornées. Elle n'accorde aucune capacité réseau à l'overlay et n'est pas présentée comme une mesure ICMP.

Les préférences de thème (apparence, style, base neutre, accents, couleurs de graphiques, polices et rayon) sont stockées dans `fxmp-settings.json` sous `themePreferences` via le plugin Store déjà autorisé aux deux fenêtres. Elles changent les tokens CSS shadcn; aucune nouvelle permission ou donnée distante n'est nécessaire. Les installateurs gardent les pages natives NSIS/WiX, avec des visuels bitmap Tauri dimensionnés selon leur schéma, et NSIS demeure en installation utilisateur sans élévation.

## Choix OpenClaw qui ne sont pas importés

- Le Windows Hub d'OpenClaw est une application native WinUI; FXMP OS cible actuellement Windows uniquement, avec Tauri comme shell desktop. Les builds macOS/Linux restent désactivés jusqu'à décision explicite de réactivation; le changement de cible ne retire pas les dépendances Linux transitives ni l'alerte glib suivie dans l'issue #7.
- Les Gateways WSL, services gérés, connexions distantes, jumelage d'appareils, commandes d'agents, MCP et politiques multi-profils répondent aux fonctions d'assistant d'OpenClaw; FXMP OS n'a pas ces surfaces.
- Les capacités séparées sont utiles quand une app possède plusieurs WebViews de confiance différente. FXMP OS a deux fenêtres locales; chacune reçoit sa propre capacité étroite.
